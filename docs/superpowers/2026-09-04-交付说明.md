## Consolidated manual-verification checklist

This supersedes every manual-verification list scattered across `task-17-18-report.md`, `task-19-20-report.md`, `task-21-22-report.md`, and this report. It is deduplicated: items a test now settles were dropped (noted below); the rest are things that genuinely require a real browser/device/OS to judge — jsdom cannot observe real focus-steal, real IME candidate windows, real touch/zoom behavior, real glyph-metric layout, or subjective animation smoothness. Each item names its failure signature.

**None of this has been performed** — no working browser-automation tool was available in any of these sessions (`chromium-cli` segfaults in this sandbox specifically; earlier sessions had no browser access at all).

1. **Focus/typing never drops — first load and after every command.** Load the page fresh and start typing immediately (no click needed); run a command and, the instant it finishes, keep typing with no click in between. **Failure:** nothing happens until you click the terminal again. **Mobile twin:** run a command on a phone and confirm the on-screen keyboard stays open afterward. **Failure:** keyboard collapses.

2. **IME candidate window tracks the block cursor, not the prompt.** During 拼音 (or any IME) input, the candidate window should visually anchor under the cursor block as it moves right through the line — check this both near the start of a line and after typing several characters. **Failure:** candidate window appears under the prompt / at a fixed wrong horizontal position instead of following the cursor.

3. **First tap on a phone.** Does the virtual keyboard open, and does iOS Safari *not* zoom the page in (or stay zoomed)? **Failure:** page visibly zooms on focus and doesn't zoom back out.

4. **Click-to-position on a long or wrapped line.** Click in the middle of a typed line (15+ characters, including one long enough to wrap to a second row) to reposition the caret. **Failure:** caret lands at the wrong character — especially check for *progressive drift* (error growing the further right you click), which is the specific symptom a prior font-size mismatch between the hidden input and the drawn text caused.

5. **Paste.** Paste a single line of text (Ctrl+V, and long-press-paste on mobile). **Failure:** drawn text doesn't update, or the cursor doesn't end up at the end of the pasted text. (No automated coverage exists for paste at all — this is a genuine gap, not just a device-dependent recheck.)

6. **Keybindings a real browser may intercept before the page ever sees them.** Note which Ctrl combos don't reach the terminal. In particular, **Ctrl+W is very likely to close the browser tab** in Chrome/Edge/Firefox (not cancellable from page JS) — warn the tester so they don't mistake losing the tab for an app bug. (The word-delete *logic* itself, and Ctrl+U/L/C, are unit-tested in `keys.test.tsx`; this item is only about the browser/OS layer no test can reach. Ctrl+A/E/K have no direct unit test either — worth a quick manual sanity check: line-start/line-end/delete-to-end.)

7. **Android soft-keyboard composing (`keyCode 229` / `key 'Process'`).** During 拼音 input on an Android device specifically, confirm committed text submits correctly on Enter and composition keystrokes don't leak into the command line. (`isComposing` is unit-tested in `PromptLine.test.tsx`; the real device sending `keyCode 229` instead is not something a synthetic event can prove.)

8. **Reverse search (Ctrl+R) caret position.** The cursor block should sit at the start of the matched substring within the matched line, not at a fixed offset — check with the match occurring at different positions in the line. (Ctrl+R's *matching* logic — walk to older matches, stop at the oldest, accept, cancel, empty-match-preserves-typed-text — is fully unit-tested in `useReverseSearch.test.tsx`; only the visual caret placement is unverified.)

9. **Theme switch: instant, no flash.** Run `theme <name>` — the whole UI should recolor immediately with no flash of unstyled content. Reload the page — it should come back already in that theme, not flash the default (`tokyo-night`) first before repainting. Open a private/incognito window where `localStorage` might throw — the terminal should still load and default to `tokyo-night` without crashing. **Failure:** any visible flash of the wrong palette, theme resets on reload, or a blank page/console error in incognito. (The "no flash on reload" property was the subject of a real fix — `useTheme.ts` switched from `useEffect` to `useLayoutEffect` — but "no visible flash" itself isn't observable in jsdom, so it stays here to confirm the fix actually holds on a real screen.)

10. **Mobile key bar keeps the keyboard open and each button works.** Tap each key-bar button (Tab, ^C, ↑, ↓, |, ~, /, -) in sequence *without* tapping the input in between. **Failure:** keyboard collapses after the first tap (would mean a real mobile browser doesn't honor `preventDefault` for blur-suppression the way the unit tests, which only check the JS event object, assume), or a button doesn't have its expected effect.

11. **Keyboard doesn't cover the input line on a touch device.** Tap the terminal to bring up the virtual keyboard — the input line should stay visible above it. **Failure:** input line hidden behind the keyboard (would mean `visualViewport` resize handling or `bottomInset`/`paddingBottom` isn't reaching far enough).

12. **Wide output scrolls within its own block, never the page.** Run a command with long lines (e.g. `tree` on deep paths). **Failure:** the whole page gains a horizontal scrollbar, or the wide line is clipped/invisible instead of scrolling in place.

13. **Boot animation's typing rhythm looks smooth.** Watch a fresh load (empty `sessionStorage`): banner + motd typing out at ~90ms/line should look smooth, no stutter, no layout jump, no flash of the prompt before the last line finishes. This is a pure rendering judgment — every *state transition* around it (keypress skips it, replay is suppressed on an already-played session, `prefers-reduced-motion` skips it) is already pinned by passing assertions in `BootSequence.test.tsx` and does not need re-checking by hand.

14. **`matrix` and boot animation, general visual polish.** Does the digit-rain / boot sequence *look* good — is the frame rate perceptible as smooth? Everything mechanically verifiable about `matrix` (timing, cleanup on unmount, no leak across repeated runs, no throw) is covered by the lifecycle tests added in this task; only the aesthetic judgment remains. `chromium-cli` is non-functional in this sandbox (segfaults on `open`), so no screenshot could be produced this round — accepted by the coordinator as unavoidable here.

15. **Live end-to-end smoke test in a real browser** (`pnpm preview`, then `help`/`about`/`projects`/`skills`, `theme nord`, `cat about.md | grep 工程`) — every one of these specific behaviors is exercised by the automated suite along the same code paths (`site.test.tsx`, `sys.test.ts`'s theme tests, `pipe.test.ts`, `kernel.test.ts`, `text/*.test.ts`), and the static-resume/server-serves-content half was confirmed via `curl` in this session — but a literal click-through was not possible for the same `chromium-cli` reason as item 14.
